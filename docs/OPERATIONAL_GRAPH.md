# Operational dependency graph and cascade baseline

CascadeShield has two separate graphs. The immutable Chennai road graph connects real OSM road nodes with legal directed road segments and supported turn restrictions. It answers route and movement questions. The operational graph connects manually configured **simulated** trucks, drivers, docks, deliveries and warehouses. It answers which explicitly assigned resources can share delay or capacity consequences. Historical road-safety, Cambridge and e-commerce records never create operational dependencies.

`OperationalDependencyGraph` builds a JGraphT `DirectedWeightedMultigraph<String, GraphEdge>` and exports the stable `OpsModels.GraphView` REST representation. JGraphT core is pinned to **1.5.3**, verified against the [official release site](https://jgrapht.org/) and its official Maven Central POM. Its [directed weighted multigraph](https://jgrapht.org/javadoc/org.jgrapht.core/org/jgrapht/graph/DirectedWeightedMultigraph.html) supports parallel typed relations. Self-links are omitted; cycles between distinct resources are permitted and handled by the baseline. The graph never modifies physical-road edges.

## Entities, direction and provenance

IDs use `TYPE:resourceId`, such as `TRUCK:T1`, `DRIVER:DR1`, `DOCK:D1`, `DELIVERY:L1` and `WAREHOUSE:W1`. Nodes include all configured resources, including unassigned resources. Different types may use the same resource ID without colliding. Lists, feature maps and edge IDs are sorted for deterministic JSON and replay comparisons.

| Directed relation | Source of the relationship | Meaning of delay exposure | Baseline weight |
| --- | --- | --- | --- |
| Truck → Driver, `ASSIGNED_DRIVER` | Explicit truck-driver assignment | Delayed work can keep its assigned driver occupied | 0.80 |
| Truck → Dock, `RESERVED_DOCK` | Explicit dock reservation | Delayed arrival/service can shift the reserved dock schedule | 0.90 |
| Truck → Delivery, `CARRIES_DELIVERY` | Explicit truck-delivery assignment | Delayed work can delay the assigned delivery | 0.95 |
| Delivery → Warehouse, `DELIVERY_TO_WAREHOUSE` | Delivery's configured destination | Lateness exposes that destination to delayed receipt | 0.70 |
| Dock → Warehouse, `DOCK_AT_WAREHOUSE` | Dock's configured warehouse | Dock service exposes its parent warehouse | 0.75 |
| Dock → waiting Truck | Computed same-dock forecast/reservation overlap or `DOCK_OVERLAP` impact | Preceding work can delay an explicitly dependent truck | `0.50 + 0.50 × min(delaySec / 600, 1)` |
| Driver → waiting Truck | Computed same-driver duty overlap or driver constraint impact | Preceding work, availability or shift limits can delay assigned work | Same delay-based rule |
| Delivery/Dock/other explicit Resource → Truck | Runtime constraint with a verified matching assignment | Identified deadline/window constraint on that truck | Same delay-based rule |

Weights are documented **rule assumptions**, bounded within `[0, 1]`; they are not learned correlations, observed freight relationships or calibrated probabilities. Features include `weightSource: DOCUMENTED_RULE_BASELINE`, assignment and reservation timing, current resource status, speed/load/deadline values, forecast dock times, computed delays and impact IDs where available. All nodes and edges use `provenance: SIMULATED`. Warehouse coordinates select locations on real geography but do not claim an observed real logistics facility.

For runtime conflicts, `Impact.truckIds` contains dependent trucks. A `TRUCK:<blocker>` reference in `Impact.resourceIds` identifies the actual preceding assignment and its incident cause; it does not create a new truck or an inferred truck-to-truck dependency. A resource→truck edge is emitted only when that truck has an explicit matching assignment. Unknown entities and unrelated resources do not produce relationships.

## Time validity and forecasting

Each edge contains `validFromSec` and `validUntilSec`, in simulated seconds relative to `State.initialClockIso`. Intervals are half open: `[start, end)`. Dock/delivery assignment exposure ends at actual dock completion once known; otherwise the forecast/reservation completion is used. Driver assignment exposure ends at road arrival, because this milestone's runtime releases the driver before dock service. Delivery exposure ends on measured simulated delivery completion; an unfinished delivery's destination relationship uses the validated operational horizon of **172,800 seconds (48 hours)**. This is separate from the truck road-trip deadline limit of 24 hours, because dock operations may continue after road arrival. Empty intervals are omitted, and graph materialization rejects nonfinite intervals and weights outside `[0, 1]`.

Forecast dock intervals use actual start when unloading has begun, otherwise the current ETA, reservation and projected start/end. The runtime fills `actualDockEndSec` with scheduled service completion when unloading starts; its positive value alone does not mark completed work. `Assignment.status: COMPLETED` closes actual occupancy. Overlap means `max(firstStart, secondStart) < min(firstEnd, secondEnd)`. Dock blocker order follows projected service order. Driver blocker order follows departure/duty order, which can differ from warehouse arrival order. Completed assignments do not create new conflicts. Unknown ETA prevents fallback forecast interval conflicts; the explicitly unavailable driver constraint can still expose its assigned truck without a fabricated ETA. Runtime-generated schedule impacts and fallback explicit interval edges can coexist as parallel edge types; per-cause maximum propagation prevents them from counting the same cause twice.

Dock ready/start/completion forecasts round **up** to the authoritative 0.1-second tick. Actual service completion uses the same ceiling, and service can begin only if that rounded completion fits the dock's opening window. Reservations and assigned-dock edits validate the rounded service duration as well as raw hours. A dependent truck ready at 10.14 seconds is ready on tick 10.2, so a preceding service ending at 10.2 creates no invented fractional overlap. Completed forecast fields canonicalize to measured service times, keeping exports independent of dashboard refresh frequency.

Shared-driver transfer validation checks adjacent trips in departure order, allowing valid multi-trip chains while requiring each preceding destination to match the next start node. When a driver is still on earlier work, a later truck remains at its actual start until that work reaches its actual destination. ETA reruns piecewise road traversal from the predicted driver-ready time; it does not add a driver wait onto road waiting that would already have expired. Route incident IDs are recalculated at that later start, preserving the distinction between direct road exposure and indirect shared-driver consequences.

The baseline evaluates unexpired current **and future** assignment intervals in the current snapshot. It therefore displays predicted downstream exposure before a queue actually forms. Expired dependencies cannot carry current risk. This snapshot baseline does not solve a global time-respecting joint scheduling/routing optimum or guarantee that every exposure path will occur. The authoritative runtime separately enforces driver/dock rules and produces realized outcomes as simulated time advances.

## Deterministic bounded propagation

`GraphRiskBaseline.predict(State, GraphView)` returns `OpsModels.CascadeView` with provider `RULE_BASED_GRAPH_BASELINE` and provenance `SIMULATED_PREDICTION`.

1. Direct road exposure comes only from actual `truck.affectedIncidentIds` calculated against its current route. Resolved/expired incidents are ignored. Each incident seed is `clamp(0.65 × directTravelRisk + 0.35 × incidentSeverity)` at the directly affected truck. Scheduled incidents may seed a forecast if that route is actually expected to encounter them.
2. Computed operational constraints seed `clamp(0.20 + 0.80 × min(delaySec / 600, 1))` at their explicit resource. Related impacted/blocking truck references retain the same incident cause (`INCIDENT:I1`) rather than inventing an independent cause. This resource seed is capped at the largest existing seed for that incident. An explicitly referenced blocker can retain a physically encountered incident after it resolves: the cap is then `clamp(0.65 × min(roadArrivalDelay / 600, 1) + 0.35 × encounteredSeverity)`, using measured arrival delay or the current estimate while still travelling. This historical cause exists only while a current operational forecast actually references that blocker; it never reseeds the now-unaffected truck directly. A constraint with no linked road incident gets its own `OPERATIONS:<impactId>` cause. Positive computed delays are required except an explicit `DRIVER_UNAVAILABLE` constraint with unknown ETA: it receives a documented 0.80 blocking score, independently of road incidents, without inventing a wait duration or arrival time.
3. For each cause independently, propagate `sourceScore × dependencyWeight`. At a node with several incoming paths from that **same** cause, retain the maximum. Perform synchronous passes, sorted by edge ID, with at most `N − 1` passes for `N` vertices and early exit when unchanged. Because all weights are at most one, cycles cannot amplify risk or improve a score by repeated traversal. Zero-weight relations carry no risk.
4. Aggregate different causes using `1 − product(1 − causeScore)`, clamped to `[0, 1]`. This is a deterministic bounded ranking rule; the mathematical form does not establish statistical independence or turn the score into a probability.
5. The affected-subgraph threshold is `clamp(0.35 − 0.20 × maximumLinkedIncidentSeverity, 0.15, 0.35)`. More severe directly linked incidents expose a wider set of dependencies. With no linked road incident the threshold is 0.35. `affectedEdgeIds` includes unexpired edges with both endpoints above threshold.

`NodeRisk.direct` indicates that a node was explicitly seeded by a road incident or computed resource constraint. Other positive scores describe indirect propagation. `causeIds` preserves cause attribution. The maximum-product rule means a common ancestor reaching a warehouse via both its dock and delivery does not spuriously amplify one incident. Distinct incidents can still jointly increase exposure at a shared downstream resource.

## Predicted versus realized consequences

Predicted schedule conflicts, ETA and cascade scores are forecasts. They are separate from current driver duty, actual dock occupancy, actual queue/unload completion and measured simulated delivery lateness. The graph consumes runtime `predictedImpacts`; it never writes simulation state, approves an action, moves a truck or fabricates an outcome. The operational runtime owns realized impacts and events. Dashboard and snapshot exports retain `SIMULATED_PREDICTION` versus `SIMULATED_OUTCOME` classifications. No baseline result is a claim of field effectiveness or model-training performance.

## Example with explicit resources

Manually assign Truck A and Truck B to the same dock at a selected simulated warehouse, with separate drivers and deliveries. Give B a dock reservation overlapping A's currently projected completion. Inject a real-road closure on A's actual route. The backend's changed ETA can shift A's service interval; a computed overlap emits Dock→B and delay predictions for B's delivery. The path is A→Dock→B→Delivery B→Warehouse. Existing assignment/dock-to-warehouse paths may form a cycle around B and Dock; they still cannot amplify the same incident seed. When trucks reach the warehouse, the runtime measures the actual queue and delivery outcomes. This is an operator-defined simulated scenario, not a historical Chennai freight record.

## Regression coverage

`OperationalDependencyGraphTest` checks explicit typed dependencies, provenance, same-resource dock overlap, occupied unloading intervals, driver release at road arrival, driver departure ordering, nonmatching-resource rejection, interval closure on completion, sorted deterministic exports and weight/time validation. `GraphRiskBaselineTest` checks a common cause arriving through multiple parents, distinct incident aggregation, cycles, expiration, severity thresholds, operational-only causes, unknown availability, expired physically encountered blocker cause retention and deterministic empty/order behavior. These use tiny clearly marked simulated fixtures to validate logic; they are not research evaluation data. Broader movement, runtime, replay, persistence and browser tests are recorded in `reports/MILESTONE_2_RESULTS.md` after execution.
